# Azure Deployment

This repo is set up to deploy as two Azure Container Apps:

- `biostack-web`: Next.js frontend
- `biostack-api`: .NET API

## Why Container Apps

The project currently targets:

- Next.js `16`
- .NET `10`
- SQLite file storage for now

Container Apps is the lowest-friction Azure option because both workloads already have Dockerfiles and the frontend needs a build-time `NEXT_PUBLIC_API_URL`.

## Required secrets

You will need:

- `Jwt__Secret`
- `PublicApiUrl`
- `FrontendUrl`
- `Smtp__Host`
- `Smtp__FromEmail`

## Deploy

Run:

```powershell
pwsh ./infra/azure/deploy-container-apps.ps1 `
  -ResourceGroup biostack-rg `
  -Location eastus `
  -BaseName biostackmissionctrl `
  -JwtSecret '<32+ char random secret>'
```

## Production-readiness boundary

- Production API startup fails closed unless `ConnectionStrings:DefaultConnection` is a Postgres connection string. SQLite at `/app/data/biostack.db` is development-only.
- The current Azure bootstrap script can create an ephemeral SQLite deployment for local or disposable validation, but that path is not production-ready and does not satisfy the backup/restore gate.
- Durable production data requires Azure Postgres plus a rehearsed backup/restore procedure with measured RPO/RTO, integrity validation, an isolated restore target, and teardown evidence.
- The backend CORS policy now reads from `Cors:AllowedOrigins`, so the deployed frontend origin must be present there.
- Passwordless email links are generated by the API. Local development exposes `/dev/auth/inbox`; production sends them through SMTP when `Smtp__Host` is configured.

The CI workflow is the authoritative release path. A successful local bootstrap or merged pull request is not release evidence; the release candidate must be verified from the exact SHA in the intended non-production environment before any production decision.
