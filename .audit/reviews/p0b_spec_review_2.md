## Ranked findings

### F1 (MAJOR) — "Degraded"/"escalate" cell semantics are used ~40 times but their normative definition is dropped from the transcription
**Claim:** The ruled source text at `P0-B-DESIGN-GATE.md` lines 95-96 defines the per-cell letters with operative content: *"**D** = degraded (allowed with mandatory evidence/explanation/validation additions)... **E** = escalate (stop ordinary output, surface escalation)."* P0-B.md's "Per-label behavior matrix" section (lines 373-375), which claims to be "transcribed verbatim... lines 93-120," restates only the bare letter key — *"cells read **A** = allowed, **D** = degraded, **R** = refused, **E** = escalate"* — and drops the parenthetical operative definitions entirely. No other Deliverables field (`numericProvenance`, `missingInputLadder`, `calibrationRequired`, etc.) restates this generic requirement that every `D` cell must carry "mandatory evidence/explanation/validation additions." `calibrationRequired` text is label-specific and does not substitute for this cross-cutting rule.
**Evidence:** `P0-B.md:373-375` vs. `P0-B-DESIGN-GATE.md:95-96`.
**Why it matters:** This is exactly the "'degraded' undefined" exploit this review was asked to hunt for. Downstream (P0-C fixtures, a future runtime-integration parcel), a builder could implement "degraded" as any cosmetically-reduced output — a disclaimer sentence, for instance — without the ruled requirement for mandatory evidence/explanation/validation additions, because the machine-readable artifact nowhere states that requirement as a structural obligation of the `D` literal itself. `matrix-fidelity`'s own definition ("every `[RULED — verbatim]` clause... matches this spec's own Deliverables text byte-for-byte") cannot catch this because the generic definition was never in the spec's own Deliverables text to begin with — the verbatim-transcription claim is itself inaccurate for this clause.
**Smallest amendment:** Add the dropped parenthetical operative definitions for `D` and `E` (and the already-present `A`/`R` definitions, for completeness) as a `"cellSemantics"` object in Deliverables item 9 (or inline in the "Per-label behavior matrix" prose), citing `P0-B-DESIGN-GATE.md:95-96` as `[RULED — verbatim]`, and require `verify-p0b.ps1` to check its presence.
**Changes a locked decision?** No — it corrects an incomplete transcription of an already-ruled clause; it adds no new product decision.

### F2 (MAJOR) — No machine-readable field carries the per-cell scope qualifiers the ruled table itself uses
**Claim:** Several ruled-table cells carry a scope qualifier that changes what the bare letter means operationally: `pregnancy-or-lactation` C1 = `R (dose-context)` (not a blanket C1 refusal), `prescription-treatment-involved` C3 = `R (for the prescribed treatment)` (not a blanket C3 refusal for the whole function). The Deliverables section defines `"behavior"` as an object keyed C1/C2/C3/C4, "each value one of `"allowed"`/`"degraded"`/`"refused"`/`"escalated"`" (P0-B.md ~line 354) — a bare enum with no field for the qualifier. The spec does carve out one ad-hoc exception for the `interaction-or-contraindication-signal` C3 `D→E` cell (`"degraded-escalates-on-strong-signal"`, lines 392-397), proving the authors recognized qualifiers need encoding for at least one cell, but the two `(dose-context)` / `(for the prescribed treatment)` qualifiers get no equivalent structural treatment and have no designated home (`calibrationRequired` is label-level prose, not a cell-level, checkable field).
**Evidence:** P0-B.md Deliverables item 9 "behavior" bullet (~line 354); per-label table rows for `pregnancy-or-lactation` and `prescription-treatment-involved` (~lines 379, 380).
**Why it matters:** This is a genuine "missing machine-readable field" (category c) and a laundry-list loophole (category b): a hostile implementation of the *eventual* runtime/fixture layer could read the JSON's bare `"refused"` literal for `pregnancy-or-lactation`/C1 and apply it to every C1 surface (over-broad refusal — safety-conservative but non-conformant to the ruled table) or, worse, could read `calibrationRequired`'s free prose as non-binding and ship an un-scoped `"refused"`→ `"allowed"` reinterpretation because the qualifier was "just calibration text, not the cell value." Either way, the qualifier that the owner actually ruled has no checkable, structural encoding, so `matrix-fidelity` cannot verify it is preserved.
**Smallest amendment:** Add an optional `"scope"` string field alongside each qualified cell (e.g., `"scope": "dose-context-only"`, `"scope": "prescribed-treatment-only"`), required wherever the ruled table's cell carries a parenthetical qualifier, and add a `verify-p0b.ps1` check that every parenthetical in the ruled table has a corresponding `"scope"` field.
**Changes a locked decision?** No — same bounded-operationalization logic as the existing `D→E` carve-out; it only makes an already-ruled qualifier machine-checkable.

### F3 (MAJOR) — "Stop conditions" section never states it is a D14 fieldwise union of the four classes' `mandatoryStopConditions`, and two health-boundary stop conditions are not traceably present
**Claim:** D14 requires: *"Controls compose field by field: union required sections, checks, stop conditions, and evidence."* `delivery-class-controls.json`'s `health-boundary.mandatoryStopConditions` is `["unsupported certainty", "prescribed-treatment direction", "red-flag bypass", "provenance loss"]`. The spec's "Deterministic verification" section explicitly performs this fold-and-adapt exercise for `minimumChecks` (a named table mapping each class's checks to a P0-B adaptation). No equivalent table or adaptation statement exists for `mandatoryStopConditions`. The spec's own "Stop conditions and standing-authorization tripwire" section is a bespoke, P0-B-specific list that reasonably covers "red-flag bypass" (locked-label-altered stop) and arguably "provenance loss" (missing-normative-input stop), but never names or adapts "unsupported certainty" or "prescribed-treatment direction" — both plausible failure modes for *this* parcel (e.g., an `[OPERATIONALIZED — bounded]` criterion asserting a certainty the cited evidence source does not support, or a `calibrationRequired` cell text that drifts toward directing alteration of a prescribed treatment).
**Evidence:** `delivery-class-controls.json` `health-boundary.mandatoryStopConditions`; P0-B.md "Stop conditions and standing-authorization tripwire" (no corresponding table or adaptation note, contrast with the "Deterministic verification" table's explicit fold).
**Why it matters:** This is the rubric's own named check — "Class-control completeness: every declared delivery class's required sections, checks, reviewer counts, stop conditions, and closure evidence present and correct (D14 fieldwise fold)." The checks and reviewer counts are demonstrably folded and verified clean (see Verification notes); the stop-conditions fold is not demonstrated with the same rigor, which is inconsistent within the same document.
**Smallest amendment:** Add a short "stop-conditions fold" note (mirroring the "Deterministic verification" table's style) explicitly mapping each of the four classes' `mandatoryStopConditions` to either an existing P0-B stop-condition bullet or an explicit `not-applicable` disposition with reasoning (privacy's two conditions are plausibly `not-applicable` given the zero-personal-data posture already stated elsewhere in the spec; health-boundary's "unsupported certainty" and "prescribed-treatment direction" are not).
**Changes a locked decision?** No — it is a completeness/traceability fix to the spec's own self-audit discipline, not a new product decision.
