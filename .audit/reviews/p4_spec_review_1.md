## Ranked findings

### F1 (MAJOR) — Validation stage 6 (`unknown-extension-point`) is specified but never proved by any of the ten required fixtures
**Claim:** The spec's own fixture set is not sufficient to catch a broken or absent implementation of document-contract-1 stage 6 ("Extension-point reference check"), so AC-P4-03's "fixture proof" claim overstates actual coverage.
**Evidence:** Document contract 1 lists stage 6 as mandatory ("if the spec declares a reference to an `extensionSections` key not present in the live registry, `"unknown-extension-point"`"). The Hard constraints bullet lists `unknown-extension-point` among the eleven failure reasons the linter must support. Yet document contract 2's ten named fixtures (`positive-ticket-spec-standard-single`, `positive-coordinator-parcel-multilabel-fold`, `positive-real-spec-p3b-cross-check`, `negative-missing-required-frontmatter-field`, `negative-capability-field-missing-on-trigger`, `negative-unknown-delivery-label-multilabel`, `negative-placeholder-entity-disguised-multilabel`, `negative-capability-claim-drift-referential`, `negative-incompatible-controls-scalar-conflict`, `negative-unrecognized-shape-path`) contain no fixture exercising an unrecognized `extensionSections` reference. `EXTENSION-POINTS.md`'s own text ("the mechanic the `negative-unknown-extension-point` fixture proves") confirms this exact fixture name/shape already exists under P3-A (`docs/specs/schemas/fixtures/p3a/negative-unknown-extension-point.json`), but that fixture is only ever exercised by P3-A's own narrower `verify-p3a.ps1`, never through P4's general `-SpecPath`/`-SyntheticSpecJson` entrypoint. verify-p4.ps1's check 6 ("For each of the ten `fixtures/p4/*.json` fixtures...") therefore can never detect a broken, missing, or mis-wired stage-6 implementation in `validate-spec.ps1`. A nonconforming linter (stage 6 absent entirely, or silently always-pass) would pass every deterministic check this spec defines.
**Smallest amendment:** Add an eleventh fixture, e.g. `negative-unknown-extension-point-reference.json`, exercising stage 6 through the general entrypoint (and bump every "ten fixtures"/"ten-fixture" reference in document contracts 2/3, AC-P4-03, check 6/8, and the Exact-allowed-surfaces list accordingly), or explicitly fold this case into one of the already-named fixtures' design and name the resulting reason in `expected`.
**Changes a locked decision?** No — this is an addition within P4's own, not-yet-dispatched scope; it does not touch any frozen P0-B/P2/P3-A/P3-B artifact.

### F2 (MAJOR) — `pathPattern` matching grammar is undefined anywhere in canon, creating a genuine two-implementer determinism gap
**Claim:** `validate-spec.ps1`'s resolution-order step 2 requires matching a real `-SpecPath` against `specShapes.*.pathPattern` strings (`docs/INITIATIVES/*/parcels/*.md`, `docs/specs/active/*.md|docs/specs/done/*.md`), but no document in the composed contract (`parcel-spec.schema.json`, `SECTION-HEADING-MAP.md`, `EXTENSION-POINTS.md`, `canon-precedence.md`) defines the matching grammar: whether `*` is glob-style (single path segment only) or regex-style (matches `/`), whether the pattern is anchored at both ends, or how the embedded `|` in the ticket-spec pattern is meant to be parsed (literal alternation vs. a single opaque string). `verify-p3a.ps1` (the only prior consumer of this field) only asserts the pinned *string literal* equals a fixed value (`verify-p3a.ps1:594-596`) — it never actually executes path matching against a real file path. P4 is the first parcel required to implement and execute this match deterministically, against real repository paths (`positive-real-spec-p3b-cross-check.json`'s `docs/INITIATIVES/biostack-governed-delivery/parcels/P3-B.md`, and `negative-unrecognized-shape-path.json`'s `docs/INITIATIVES/biostack-governed-delivery/CHARTER.md`), and the spec supplies no grammar. Two honest builders could plausibly diverge (e.g., one implementer treats `*` as `[^/]+`, another as `.+`; one implementer treats `|` as regex alternation applied verbatim to the stored string, another as two separately-stored sub-patterns) without either violating the letter of this spec.
**Smallest amendment:** Pin the exact matching grammar in document contract 1 (e.g., "`*` matches one or more characters excluding `/`; the pattern is a POSIX-anchored full-string glob; `|` is a plain string-split delimiter producing independent alternative glob patterns") and require `verify-p4.ps1` to assert it deterministically against the two real fixture paths that currently exercise it.
**Changes a locked decision?** No — clarifies an underspecified mechanic P4 is the first to execute; does not alter `parcel-spec.schema.json`'s stored literal.

### F3 (MINOR/MAJOR-adjacent) — Stage 2's "unrecognized status value... named accordingly" leaves the actual `reason` literal unnamed, and no fixture exercises it
**Claim:** Document contract 1 stage 2 states an unrecognized `status` value "is named accordingly" but never names the literal reason string, and the Hard Constraints' eleven-item closed reason vocabulary (`unknown-label`, `empty-required-axis`, `incompatible-controls`, `missing-required-field`/`missing-required-frontmatter-key`, `missing-required-section`, `placeholder-violation`, `unknown-extension-point`, `unrecognized-shape`, `capability-claim-drift`, `invalid-function-review-status`, `premature-public-enablement-claim`) contains no reason literal that self-evidently covers an invalid `status` value. (`guidance_classes`/`substance_function_risk` membership is covered by fold-engine's own step-1 `unknown-label` check per `fold-engine.md`'s "the fold consumes: a declared label set (`deliveryClasses`, `guidanceClasses`, `substanceFunctionRisk`)... reject with `unknown-label` on any miss," but `status` is not one of the three axes the fold consumes, so it is not covered by that mechanism.) No fixture in document contract 2 exercises an invalid `status` value either, so this gap is both unnamed and unverified.
**Evidence:** P4.md document-contract-1 stage 2 text; Hard constraints bullet's eleven-reason list; `fold-engine.md` "The fold consumes" paragraph.
**Smallest amendment:** Name the literal reason for an invalid `status` value explicitly (e.g. add `invalid-status` to the closed reason vocabulary) and add or extend a fixture to prove it.
**Changes a locked decision?** No — this is a new leaf reason local to P4's own output vocabulary, not a restatement of any frozen P0-B/P2/P3-A/P3-B rule.

### F4 (MINOR) — Overclaimed cross-verifier "field for field" agreement with `verify-p3b.ps1` check 9
**Claim:** Document contract 2's `positive-real-spec-p3b-cross-check.json` description and check 7 of "Deterministic verification" both assert that `expected.foldSummary`/`expected.boundFieldsChecked` "must agree, field for field, with what `verify-p3b.ps1`'s own check 9 already established for this exact file." In the actual `verify-p3b.ps1` source, check 9 (`verify-p3b.ps1:677-717`) invokes `Test-CapabilitySafetyOverlay`, which returns only `{Result, Reason}` (`verify-p3b.ps1:335-370` and onward) — it never computes or exposes a `foldSummary` (the D14 routing-output object) or a `boundFieldsChecked` array at all. There is therefore nothing in check 9's own output for a `foldSummary`/`boundFieldsChecked` comparison to "agree" against; the claim that check 9 "already established" these fields is inaccurate.
**Evidence:** `docs/specs/scripts/verify-p3b.ps1` lines 335-370 (`Test-CapabilitySafetyOverlay` return shape) and 677-717 (check 9's use of it).
**Smallest amendment:** Narrow the claim to what check 9 actually establishes (Result/Reason agreement on the capability-safety-overlay outcome) and describe `foldSummary` agreement as a new computation P4 performs independently (since P3-B never computed a D14 fold for its own file), not as something check 9 "already established."
**Changes a locked decision?** No — corrects a factual description of a read-only prior artifact; does not alter `verify-p3b.ps1` itself.
