## Ranked findings

### F1 (MAJOR) — "26-file" cardinality in document contract 7 / AC-P3A-07 contradicts the spec's own dynamic-BaseCommit model and is already empirically false
**Claim:** The spec hardcodes "the identical 26-file set P2's `AXIS-REGRESSION-MAP.md` already enumerates" as the expected shape of `REAL-SPEC-COMPATIBILITY-SET.md` (document contract 7, line 611) and restates it as an acceptance gate — "`REAL-SPEC-COMPATIBILITY-SET.md` has exactly one row per the **26-file P2 census set**" (AC-P3A-07, lines 702-703) — while elsewhere the same spec explicitly and correctly warns that `BaseCommit` is re-pinned live at Gate 2 dispatch time and "`main` has continued to advance since this shaping pass (including further spec-corpus... activity)" (Lineage and dependencies), and the actually-enforced verifier check (check 10) computes the row count **dynamically**: `require the row count to equal (git ls-files docs/specs/active docs/specs/done | at BaseCommit).Count - 2` (line 811) — not a literal 26.

**Evidence (empirically verified, not hypothetical):** `git ls-files docs/specs/active docs/specs/done` on the current worktree HEAD already returns 29 paths (27 excluding the two READMEs) — one more than the "26" figure, because `docs/specs/active/BIO-FE-002-onboarding-route-consolidation.md` was added (commit `fadb968`) *after* P2's `BaseCommit` (`f812dc3`, the commit `AXIS-REGRESSION-MAP.md` is pinned to). `AXIS-REGRESSION-MAP.md` contains exactly 26 data rows and does not mention `BIO-FE-002` at all. Since P3-A's real `BaseCommit` will be re-resolved at Gate 2 time (later than `main`'s current HEAD, which is already past 26), the real corpus at dispatch will almost certainly be ≥27 files, not 26.

This creates two concrete problems the spec does not resolve:
1. **Ambiguity for the builder/reviewer**: AC-P3A-07's literal "26-file P2 census set" phrasing and check 10's dynamic `.Count - 2` definition will diverge at the real `BaseCommit`. A builder could cite the AC prose to justify reusing P2's stale 26-file list (silently omitting `BIO-FE-002` and any other post-P2 additions), which would satisfy the letter of AC-P3A-07 while violating AC-P3A-07's own stated purpose (compatibility coverage of "every file" in the real, current corpus) and the Carry-over #2 intent (a genuine structural pass over the real corpus). This is exactly the letter-vs-spirit evasion this review was asked to probe for.
2. **No defined behavior for corpus files added after P2's close.** Document contract 7's second bullet instructs: "`AXIS-REGRESSION-MAP disposition` is copied verbatim (read-only citation, not re-derived) from P2's shipped `AXIS-REGRESSION-MAP.md` row for that file." For a file like `BIO-FE-002` that has no corresponding row in the frozen `AXIS-REGRESSION-MAP.md`, there is nothing to copy. The spec gives no literal fallback value (e.g. `not-yet-censused`) for this cell, unlike its careful handling of the `*.shaping-result.json` `n/a` case in the very next bullet.

The spec already demonstrates the correct pattern for this exact kind of "informative but not literal" number elsewhere — document contract 2's 46-terms sentence explicitly disclaims: "the builder must derive this count live from the file, not copy the number from this sentence, which is informative context only." No equivalent disclaimer exists for the "26-file" figure in document contract 7 or AC-P3A-07.

**Smallest amendment:** (a) In document contract 7 and AC-P3A-07, replace "the identical 26-file set"/"26-file P2 census set" with a disclaimer parallel to document contract 2's 46-terms sentence, e.g. "the live file set at the re-pinned `BaseCommit` (26 files as of P2's `BaseCommit` lineage; the builder must derive the current count live via `git ls-files`, not copy this number, which is informative context only)." (b) Add one sentence to document contract 7 defining the literal `AXIS-REGRESSION-MAP disposition` cell value for any row whose file has no corresponding entry in the frozen `AXIS-REGRESSION-MAP.md` (e.g. `not-yet-censused (added after P2 BaseCommit)`), and require `Agreement` for such rows to be `flagged-for-human-review` rather than silently computed.

**Does it change a locked decision?** No — it tightens wording and closes an ambiguity gap; it does not alter any frozen contract, hash, or acceptance criterion's substance, only its literal cardinality framing.
