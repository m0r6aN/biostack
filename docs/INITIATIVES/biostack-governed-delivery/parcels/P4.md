## Objective

Ship BioStack's **dependency-light, general-purpose, invocable spec linter** — the reusable
`validate <path>` entrypoint P3-A's own spec explicitly deferred to this parcel — plus a focused
set of positive and negative fixtures proving it, including multi-label and missing-field cases,
exactly as the charter names this parcel's scope. The linter validates a parcel or ticket spec
against the **whole governance contract accumulated so far**, read live, never restated or
re-decided:

1. `parcel-spec.schema.json` (P3-A) — recognized spec shapes, required frontmatter keys, the
   closed `status` vocabulary, fold-live required-section derivation, and the no-placeholder rule
   (including its nine-step `placeholderNormalizationSteps` pipeline).
2. `CAPABILITY-FIELD-MAP.md` (P3-B) — the six bound frontmatter fields
   (`function_review_status`, `function_review_owner`, `capability_claim`, `numeric_provenance`,
   `missingness`, `escalation`) and their live cross-reference rules against
   `product-capability-safety-contract.json`.
3. `classification-axes.schema.json` / `delivery-class-controls.json` / `fold-engine.md` (P2) —
   the closed label vocabularies and the D14 fieldwise fold, including its **multi-label**
   composition (union required sections and checks, maximum reviewer count, intersection
   standing-authorization eligibility, and the `incompatible-controls` stop for a genuine scalar
   conflict).
4. `product-capability-safety-contract.json`/`.md` (P0-B, frozen) — the sole, frozen source every
   `capability_claim`/`numeric_provenance`/`missingness`/`escalation` live cross-reference rule
   resolves against; the linter re-resolves every such reference **at validation time**, against
   the live file, rather than trusting a cached or pre-computed answer, so a spec's claimed value
   either matches the frozen contract's own live value exactly or the linter reports drift.

**Dependency-light (the charter's own term, operationalized here):** the linter is implemented in
the same no-network, PowerShell-only, standard-library-only style every prior verifier in this
initiative already uses (`verify-p1.ps1` through `verify-p3b.ps1`) — no external package, module,
runtime, or network call of any kind; every input is a file already present in this repository,
read directly from disk.

**Scope boundary (the three load-bearing exclusions this parcel exists to honor — stated
explicitly, per this parcel's own dispatch instruction):**

- **P4 decides nothing about product allowed-outputs.** Every live cross-reference rule the
  linter evaluates compares a spec's declared value against `product-capability-safety-contract.json`'s
  own, already-frozen value; P4 invents no new allowed/degraded/refused/escalated behavior,
  applicability criterion, provenance origin, missing-input rung, function-review rule, or
  escalation rule. That contract remains P0-B's, exclusively.
- **P4 performs no review enforcement.** The linter reports a structural `"valid"`/`"invalid"`
  result with a named reason; it does not gate, block, or automatically fail a reviewer's or
  coordinator's approval decision, does not enforce reviewer independence or read-only status,
  does not reproduce review disagreement, and wires into no CI or dispatch-guard mechanism. That
  is exclusively P7's (review enforcement) and P5's (CI governance) territory, both not yet
  shaped.
- **P4 produces no closure or evidence contracts.** The linter emits a per-invocation structural
  result object (Required document contract 1, below); it does not define an
  acceptance-to-delivery-evidence mapping, a review-record contract, a closure manifest, or a
  distinct evidence namespace for any future parcel's own closure. That is exclusively P6's
  territory, not yet shaped.

**Structural validation only (restated, inherited verbatim from P3-A's own disclaimer, which this
parcel composes rather than re-derives):** a `"valid"` result from `validate-spec.ps1` asserts
frontmatter-key presence, closed-vocabulary membership, fold-live required-section resolution,
placeholder absence, and live bound-field agreement **only**. It never asserts that a section's
content is substantive, correct, non-duplicative, or product-accurate, and it never asserts that a
declared capability claim's behavior is actually achievable at runtime — both remain human
reviewer judgment (dual review, charter D8) and P0-C's fixture proof, respectively, neither of
which this parcel performs or claims to perform.

## Deliverables

### Required document contract 1: `docs/specs/scripts/validate-spec.ps1` (new)

The general-purpose, invocable linter. A single PowerShell script exposing one externally callable
entrypoint, `Invoke-SpecValidation`, and a CLI surface:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File docs/specs/scripts/validate-spec.ps1 `
  -SpecPath <path-to-real-file> `
  [-RepoRoot <path>]
```

and, for fixture/test invocation (so the same, single implementation validates both a real file on
disk and an inlined synthetic spec, never two divergent code paths):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File docs/specs/scripts/validate-spec.ps1 `
  -SyntheticSpecJson <path-to-fixture-input.json> `
  [-RepoRoot <path>]
```

**Resolution order (deterministic, no content sniffing):**

1. If `-SyntheticSpecJson` is given, parse that JSON file's `frontmatter` (an object) and
   `headings` (an array of heading-text strings standing in for the file's actual ATX heading
   set) directly, skipping disk-path shape detection — the caller supplies the shape explicitly
   via `frontmatter.delivery_classes`/`guidance_classes`/`substance_function_risk` and an explicit
   `declaredShape` key (`"coordinator-parcel"` or `"ticket-spec"`), exactly mirroring P3-A's own
   `syntheticSpec` convention (`frontmatter`/`headings` keys).
2. Otherwise, resolve `-SpecPath` against `parcel-spec.schema.json`'s `specShapes.*.pathPattern`
   entries (read live): a path matching `docs/INITIATIVES/*/parcels/*.md` is `coordinator-parcel`
   shape; a path matching `docs/specs/active/*.md` or `docs/specs/done/*.md` is `ticket-spec`
   shape; any other path is `unrecognized-shape` and the function returns immediately with that
   result — it never guesses. For a resolved path, read the file's leading YAML frontmatter block
   and its Markdown ATX heading set (`^#{2,3}\s+.+$` lines) directly from disk.

**Validation stages (each composed, read-live, from the already-shipped source named in
parentheses — none reimplemented or copy-pasted):**

1. **Frontmatter-key presence** — every key in `requiredFrontmatterKeysCommonToBothShapes`
   (plus the shape's own `idFrontmatterKey`) must be present; missing keys produce
   `"missing-required-frontmatter-key"`, naming every missing key (`parcel-spec.schema.json`).
2. **Closed-vocabulary membership** — `status`, `delivery_classes`, `guidance_classes`,
   `substance_function_risk` values must each be closed-vocabulary members; an unrecognized
   `status` value, or any `delivery_classes` label failing the fold's own vocabulary check (next
   stage), is named accordingly.
3. **D14 fieldwise fold over `delivery_classes`** — invoke `fold-engine.md`'s algorithm, unmodified,
   against `delivery-class-controls.json`, in its exact pinned order: validate every label
   (`"unknown-label"` on miss), reject empty `delivery_classes` (`"empty-required-axis"`), check
   `scalar-exact-match-required` fields for disagreement across every declared label
   (`"incompatible-controls"`, halting before any further resolution — this is the stage that
   proves **multi-label** composition: two or more declared `delivery_classes` labels are folded
   together, not evaluated independently), resolve `max-scalar`/`union-set`/`intersection-boolean`
   fields, and produce the live `requiredSpecAdditions` union plus reviewer-count/standing-
   authorization/merge-gate outputs (`routing-output.schema.json`-shaped).
4. **Fold-live required-section resolution** — resolve the stage-3 union against the spec's actual
   heading set via `SECTION-HEADING-MAP.md`'s normalization, distinct-heading-per-term, and
   anti-heading-soup rules, unmodified (`"missing-required-section"` on any unsatisfied term).
5. **Placeholder scan** — apply `placeholderNormalizationSteps`'s nine-step pipeline, in its exact
   pinned order, to every frontmatter value and heading/body text available to the validator, then
   test both `noPlaceholderPatterns` regexes (`"placeholder-violation"` on any post-normalization
   match).
6. **Extension-point reference check** — if the spec declares a reference to an
   `extensionSections` key not present in the live registry, `"unknown-extension-point"`.
7. **P3-B capability-field binding** — for each of `CAPABILITY-FIELD-MAP.md`'s six rows, evaluate
   its "Required when" trigger against the spec's declared `guidance_classes`/
   `substance_function_risk`/already-resolved `capability_claim` entries; on an unsatisfied
   required-when condition with the field absent, `"missing-required-frontmatter-key"` naming that
   field; on a present field whose value shape or closed-vocabulary membership is wrong,
   `"invalid-function-review-status"` (that field only) or the shape-specific named reason; on any
   live cross-reference mismatch against `product-capability-safety-contract.json` (behavior value,
   locked-origin membership, safety-material rung mapping, preemption stage/output type,
   `publiclyEnabled` agreement), the already-named reasons `"capability-claim-drift"` or
   `"premature-public-enablement-claim"` — every one of these seven reasons is reused verbatim from
   P3-A's/P3-B's own closed vocabulary; **this parcel introduces no new named failure reason**.

**Output contract:** a single JSON object written to stdout, schema
`"biostack.p4-validate-spec-output.v1"`, carrying `specPath` (or `"<synthetic>"`), `shape`,
`result` (`"valid"`, `"invalid"`, or `"unrecognized-shape"`), `reason` (`null` when `"valid"`, one
of the seven reused reasons above otherwise), `detail` (an object naming the offending key/label/
field, matching each reason's own existing detail shape from P2/P3-A/P3-B), and, when `shape` is
not `"unrecognized-shape"`, `foldSummary` (the stage-3 routing-output object verbatim) and
`boundFieldsChecked` (an array naming every `CAPABILITY-FIELD-MAP.md` row actually evaluated and
each row's own pass/fail). Exit code is `0` when `result` is `"valid"`, `1` otherwise — this is the
linter's own pass/fail signal for its one invocation; it is **not** wired into any CI pipeline or
dispatch guard by this parcel (P5's/P7's territory, out of scope here).
