## Objective

Define BioStack's **deterministic, machine-checkable risk-taxonomy and routing substrate**: the
schemas for the three orthogonal classification axes fixed by charter decision D14 (delivery
class, product guidance class, substance/function risk), the closed label vocabulary and
applicability metadata for each axis, a generic fieldwise composition fold that implements D14
exactly (union additive obligations, maximum reviewer count, intersection of standing-
authorization eligibility, union of every triggered human-approval gate, and a stop on
incompatible controls), and the routing outputs the fold produces: required spec sections,
minimum deterministic checks, reviewer count, standing-authorization eligibility, mandatory stop
conditions, and required closure evidence for any declared combination of labels.

P2 is schema and composition mechanics only. It does not implement the general spec linter (P4),
the generic parcel/template contract (P3-A/P3-B), closure/evidence contracts (P6), review
enforcement (P7), or any per-label product allowed/degraded/refused/escalated behavior for
substance/function risk (P0-B). It proves its own mechanics with its own fixtures and verifier;
it does not retrofit every existing active spec.

## Hard constraints

- **No product allowed-output binding.** P2 must not define, imply, or encode which substance/
  function-risk labels permit, degrade, refuse, or escalate which product outputs. That
  determination belongs exclusively to P0-B. Every substance/function-risk label entry in
  `classification-axes.schema.json` must carry `"allowedOutputBindingStatus":
  "out-of-scope-for-P2"` and `"controlBindingStatus": "deferred-to-P0-B"`, and
  `fold-engine.md` must state plainly that recording a substance/function-risk label adds no
  required sections, checks, reviewer weight, or stop condition under P2.
- **No inherited delivery-class content.** The axis-declaration file
  (`classification-axes.schema.json`) must not inline any delivery class's required sections,
  checks, reviewers, eligibility, stops, or evidence. All delivery-class control content lives
  only in `delivery-class-controls.json`, referenced by name from the axis file. A spec that
  declares a delivery-class label receives only the controls the fold computes for the labels it
  actually declares — never every label's content by default.
- **Generic, production-independent mechanics (D1/D2/D4).** The fold engine and schemas are
  general composition mechanics, not product capability semantics. No file under this parcel's
  surfaces may add a runtime, package, build, workflow, or production dependency, and none may
  define product capability, claim, or evidence semantics (that is P3-B/P0-B territory).
- **No `TBD`.** No file created or modified by this parcel may contain the literal markers
  `TBD`, `TODO`, `FIXME`, `{{...}}` placeholder syntax, or an unresolved decision. Where a value is
  genuinely not yet defined by an earlier parcel, the schema must use an explicit, closed,
  non-placeholder status literal (for example `"deferred-to-P0-B"`), never a blank or `TBD` cell.


The label arrays are the charter's closed vocabularies verbatim and in the charter's listed
order. `deliveryClass.labels` must have exactly 8 entries, `productGuidanceClass.labels` exactly
4, `substanceFunctionRisk.labels` exactly 10. Every axis must declare `"multiLabel": true` (D14).
Each axis object also declares, per label, an `applicabilityField` record (a sibling map keyed by
label name) with exactly these keys:

- `fieldName`: the **fold-input key** (camelCase: `deliveryClasses`, `guidanceClasses`, or
  `substanceFunctionRisk`) used in fixtures, fold-engine input, and `routing-output.schema.json`.
  The corresponding **frontmatter key** a spec author sets in a spec's YAML frontmatter is the
  snake_case form of the same name (`delivery_classes`, `guidance_classes`,
  `substance_function_risk` respectively) — this is the existing convention already used by every
  spec in `docs/specs/active/` and `docs/specs/done/` that declares these fields. `fieldName` pins
  the fold-input key; the frontmatter-key mapping above is the authoritative camelCase-to-
  snake_case correspondence for `AXIS-REGRESSION-MAP.md` and any future spec authoring.
- `determinationAuthority`: who decides applicability — literal `"spec-author-at-shaping-time"`
  for `deliveryClass` and `productGuidanceClass` (the charter already defines what each label
  means; a human applies that meaning when shaping a spec), and literal
  `"deferred-to-P0-B-deterministic-criteria"` for `substanceFunctionRisk` (no deterministic
  per-label applicability test exists until P0-B defines one).
- `status`: `"defined"` for `deliveryClass` and `productGuidanceClass` labels, `"deferred"` for
  every `substanceFunctionRisk` label.

Each axis's `productGuidanceClass` and `substanceFunctionRisk` entries may be declared on a spec
as an empty array (`[]`) to mean "no label from this axis applies." An empty array adds no stop,
no obligation, and no `applicabilityField` consequence; it is the sole correct representation of
"not applicable" for these two axes. The literal string `"not-applicable"` (or any other string)
is never a closed-vocabulary label on any axis and must not be used inside `deliveryClasses`,
`guidanceClasses`, or `substanceFunctionRisk` arrays; `AXIS-REGRESSION-MAP.md` must treat any
existing spec's literal `"not-applicable"` entry on these fields as a non-closed-vocabulary value
requiring `needs-reconciliation` (replace with `[]`), not as a pre-existing valid label.

This `applicabilityField` structure is metadata about *how a label gets attached to a spec*; it
is never itself a source of additional obligations — only `delivery-class-controls.json`,
through the fold, produces obligations.

### 3. `fold-engine.md`

`## Field-type taxonomy` must define exactly these four field types and bind each
`delivery-class-controls.json` field to one:

- `union-set` — `requiredSpecAdditions`, `minimumChecks`, `mandatoryStopConditions`,
  `requiredClosureEvidence`, `additionalMergeGate` (collected into a deduplicated set, dropping
  `null`). Each `union-set` input field is renamed on the routing output: `requiredSpecAdditions`
  stays `requiredSpecAdditions`, `minimumChecks` becomes `requiredChecks`,
  `mandatoryStopConditions` stays `mandatoryStopConditions`, `requiredClosureEvidence` stays
  `requiredClosureEvidence`, and `additionalMergeGate` becomes `mergeGates`. These are the only
  two renames in the fold (`minimumChecks`→`requiredChecks`, `additionalMergeGate`→`mergeGates`);
  every other field keeps its input name on the output.
- `max-scalar` — `reviewers`. For `migration`, first resolve its conditional sub-rule using the
  caller-supplied `conditionalInputs.userDataOrProductionSchemaAffected` boolean (missing input
  when `migration` is selected is a **stop**, not a default); then take the maximum resolved
  integer across all selected classes.
- `intersection-boolean` — `dispatchEligibility`/`mergeEligibility`. Resolve each selected class's
  literal to a boolean (`"eligible-when-named"` resolves to `true` once the parcel is in fact
  explicitly named at Gate 2, which the fold assumes as a precondition of being invoked at all).
  The fold computes **two separate intersections**: `dispatchIntersection` is the AND of every
  selected class's resolved `dispatchEligibility` boolean, and `mergeIntersection` is the AND of
  every selected class's resolved `mergeEligibility` boolean. The single output field
  `standingAuthorizationEligible` is then `dispatchIntersection AND mergeIntersection` — the fold
  never exposes `dispatchIntersection`/`mergeIntersection` separately; only their conjunction is
  emitted. Today all 8 classes resolve `true` on both fields, so both intersections and their
  conjunction are always `true` — this field type exists so a future class that is *not* eligible
  on either field can correctly veto standing authorization without a fold-engine redesign.
- `scalar-exact-match-required` — reserved for any future field where two selected classes must
  assert identical literal values (no such field exists in `delivery-class-controls.json` today,
  since the charter's only scalar is `reviewers`, which is `max-scalar`, not exact-match). This
  type exists for forward compatibility (e.g., a future per-label allowed-output determination,
  which is explicitly out of scope for P2) and is proven only by the synthetic fixture
  `negative-synthetic-scalar-conflict.json`, which exercises the engine directly with a
  fixture-only field named `testOnlyScalarField` that is not part of the real taxonomy.

`## Algorithm` must specify, in order: (1) validate every declared label against its axis's
closed vocabulary and reject with `unknown-label` on any miss; (2) reject with
`empty-required-axis` if `deliveryClass` has zero declared labels (every spec must declare at
least `standard`); (3) for every `scalar-exact-match-required` field present among the resolved
per-class control sets, if selected classes disagree, stop with `incompatible-controls` and
compute nothing further; (4) resolve `max-scalar` fields, stopping with
`missing-required-field` if a required conditional sub-input is absent; (5) union the
`union-set` fields; (6) intersect `intersection-boolean` fields — separately AND every selected class's
`dispatchEligibility`, separately AND every selected class's `mergeEligibility`, then AND those
two intersection results together to produce the single `standingAuthorizationEligible` value;
(7) pass `productGuidanceClass`
and `substanceFunctionRisk` declared labels straight through into `recordedGuidanceClasses` /
`recordedSubstanceFunctionRisk` without adding obligations; (8) emit the routing output.

## Dual review

Per the charter's P2 entry and D8, this is an architecture/risk-sensitive parcel: **two
independent, fresh-session, read-only adversarial reviewers**, who do not see each other's
findings, each receive the same approved spec hash, `BaseCommit`, builder commit, worktree path,
Gate 2 record, authorization identities, and the complete evidence bundle. Each review covers: D14
fold correctness against every fixture (including re-deriving the multi-label and
missing-conditional-input cases by hand), closed-vocabulary and no-inheritance fidelity
(AC-P2-01/06), the charter overlay-table free-text fidelity check that the verifier cannot
automate (AC-P2-02), the no-allowed-output-binding constraint (AC-P2-05), scope and frozen-surface
integrity, and every acceptance item. The coordinator reproduces any disputed finding before
triage; reviewers never fix the parcel; rework returns to the same builder only through a new
scoped directive and reruns every deterministic check and both reviews.

## Standing authorization and tripwire

P2 remains inside the charter's P1-P7 standing authorization **only while both of these hold**:

1. P2 changes only governance mechanics — schema, composition fold, routing output, and their
   proof fixtures — and touches no production surface (`frontend`, `backend`, `contracts`,
   `.github` all remain byte-identical to `BaseCommit`, enforced by check 4/AC-P2-08).
2. P2 makes no product allowed-output decision — it assigns no allowed, degraded, refused, or
   escalated behavior to any substance/function-risk label (AC-P2-05), and defers all guidance-
   class and substance/function-risk control binding to P3-B and P0-B respectively.

**Tripwire:** if, during shaping, review, or rework, any proposed change to this parcel would (a)
touch a production surface, (b) assign allowed/degraded/refused/escalated product behavior to a
substance/function-risk label, (c) redefine a closed-vocabulary label's meaning rather than
compose its already-charter-defined controls, or (d) require a `scalar-exact-match-required`
field to carry real (non-synthetic) product-output content, the coordinator stops immediately,
does not dispatch or merge under standing authorization, and returns to the developer for an
explicit human gate, per the charter's stop conditions and the exclusion that no standing
authorization is inferred for product allowed-output decisions.

## Regression story

Prior to P2, `docs/specs/active/*.md` frontmatter already uses ad hoc classification fields
inconsistently: some specs (`BIO-PAIRWISE-001` through `006`, `BIO-KEON-001`, `BIO-KEON-002`)
declare `delivery_classes`/`guidance_classes`/`substance_function_risk` directly (pre-figuring
P2's axes without a closed schema behind them); others (`BIO-LOCAL-003`, `BIO-LOCAL-004`,
`BIO-LOCAL-009` through `011`) use only an ad hoc `risk:`/`routing_class:` pair with values like
`elevated` that are not charter delivery-class labels at all. P2 does not silently declare these
compatible. `AXIS-REGRESSION-MAP.md` (required document contract 6, AC-P2-07) is the one-time,
read-only census that makes every such gap explicit, with a named `Disposition` for every file,
so that no spec is left in silent incompatibility with the new schema. Reconciling the flagged
specs' frontmatter is out of scope for P2 (P2 does not edit other parcels' specs) and is left as
an explicit, visible finding for a future reconciliation parcel or P4's general linter to enforce.

## Stop conditions

Stop and return to the coordinator if:

- Any required target path is absent or materially different from the contract assumed here.
- A fixture's `expected` object cannot be derived deterministically from the Algorithm section
  without a human policy call (this would mean the fold is underspecified, not that the builder
  should guess).
- P2 would need to define P0-B's per-label allowed-output criteria, P3's generic parcel/template
  schema, P4's general linter, or P6/P7's closure/review-enforcement contracts.
- The regression map would require editing any existing active/done spec to "fix" its
  classification fields.
- The production-readiness initiative or release verdict would change.
- A branch, worktree, base commit, spec hash, owner, or reviewer assignment is ambiguous.
- Any deterministic check fails twice, a frozen contract must change, or a reviewer finds an
  out-of-scope effect, or the standing-authorization tripwire above fires.

## Rollback

P2 is documentation/schema-only. Rollback is a normal revert of the P2 implementation commit on
its isolated branch, followed by the same scope, frozen-surface, fixture, and placeholder checks.
Do not delete or rewrite unrelated worktrees, branches, history, or ambient untracked files.
